# Engine verification

The desktop group uses real Qt controls and a real engine transfer; it verifies pause/resume, independent checksum, filters, details, Save/Cancel settings, history reopening, validation feedback, deletion, renders, and an event-loop heartbeat. See [desktop checks](DESKTOP.md).

Run `ctest --preset release` and `ctest --preset debug` sequentially after their corresponding builds. Twelve groups cover dependency lifecycle, two Qt startup/rendering checks, engine units, HTTP/HTTPS integration, adaptive policy, buffered writes, cross-process recovery, queue, desktop, native browser protocol, and extension controller. Python 3.10+ is needed only for integration/benchmark servers; Node.js adds the extension controller group. Neither is required by the native application. If Node is absent at configure time, CMake reports that the separate extension test remains necessary. Test output/timing are correctness evidence; separate repeated runs provide benchmarks.

The queue group runs real concurrent transfers, independently checks their SHA-256, tests global/per-origin limits and byte pacing, and verifies priorities, encrypted SQLite/WAL, settings/history persistence, exclusive ownership, pause/cancel/removal, forced process death, recovery, and corruption failure. See [queue architecture](QUEUE.md).

## Native checks

`tests/EngineTests.cpp` verifies response isolation, 64-bit range parsing, invalid/ambiguous headers, bounded input, strong/weak validators, and filename handling. Scheduler checks establish complete nonoverlapping coverage, including totals above 4 GB.

File tests perform out-of-order writes, verify known SHA-256 output, reject incorrect checksums/sizes, preserve existing partials/destinations, simulate a destination appearing before rename, reject invalid names/offsets, and truncate stale bytes for fallback. A real sparse NTFS file is written and read above offset 4 GB, then finalized at the correct 64-bit length. Sparse allocation avoids consuming 4 GB of disk; production segmented downloads reserve actual disk space.

## Controlled network checks

`tests/IntegrationTests.py` binds loopback with OS-assigned ports. Deterministic small and 17 MiB payloads are checked byte-for-byte and by SHA-256. Five fixed chunks require reassignment after the initial four concurrent connections. Request records check identity encoding, conditional requests, nonoverlapping coverage, and connection limits.

Scenarios cover advertised/unadvertised ranges; ignored ranges; missing/weak ETags; malformed probes; known/unknown lengths; chunked framing/trailers; interim responses; redirects; empty/one-byte files; fallback after a range transmits data; incorrect ranges/totals; version changes; short/oversized bodies; conditional errors; HTTP 401/403/404/429/500/503; encodings/ambiguous lengths; disconnects; timeouts; wrong/invalid checksums; unsafe schemes/credentials; existing files; and worker cancellation.

HTTPS exercises successful segmented/streaming requests with explicit test trust, a restricted loopback CONNECT proxy, untrusted-certificate rejection, hostname mismatch, and prohibited downgrade. Ambient proxy variables are excluded from fixture requests. The fixture uses a self-signed test root as its loopback server certificate. Its public disposable key/certificate are documented in `tests/fixtures/README.md`. Verification is never disabled and no certificate is added to Windows' trust store. Certificates expire in October 2036.

The fixture serves HTTP/1.1, including TLS. HTTP/2 capability is checked by the foundation test and requested by the engine when ALPN permits, but HTTP/2 wire behavior is not exercised here. HTTP/3, public-network throughput, IDM performance comparisons, physical power loss, an actual Windows reboot, and disk-full behavior are not claimed as verified. Actual results are in [development progress](DEVELOPMENT_PROGRESS.md).

## Adaptive-policy checks

Native units inject explicit times and bytes to check exact rates, smoothing, stalled windows, monotonic inputs, peak sampling, startup limits, growth/retention/rollback, sustained-loss backoff, disk pressure, manual-mode stability, and latency/chunk bounds. Resizing a scheduler repeatedly verifies contiguous coverage beyond 8 GB without allocating a large file.

`tests/PerformanceTests.py` runs 12 scenarios: fixed 1/4/8/16 limits, a small automatic file, automatic growth on per-connection caps, rollback on shared-bandwidth limits, heterogeneous fast/slow workers, automatic streaming, delayed streaming headers with a weak validator, observer exceptions, and invalid options. Every completed file has an independent SHA-256 and size check. The fixture records exact network ranges/validators, verifies no overlaps/gaps and hard limits, and validates progress stages/counters/rates/ETA. Delayed headers verify that the one-byte probe length never appears as the full file size. These tests intentionally shape loopback traffic; benchmark throughput values are kept out of correctness assertions.

Phase 2's 52 HTTP/HTTPS scenarios run with explicit fixed 4-connection/4 MiB settings and zero retries to preserve their failure/correctness regression baseline. The adaptive group checks the automatic policy. Benchmark execution and its separate limitations are in [benchmarks](BENCHMARKS.md).

## Recovery checks

`tests/RecoveryTests.py` uses separate native processes and a controlled HTTP/1.1 server. It verifies resumed SHA-256/size independently, combines saved and newly requested intervals to prove complete nonoverlapping coverage, and asserts that saved ranges are never refetched. An actual forced process termination tests recovery from the last durable checkpoint; a competing worker is refused while the first owns the file.

Scenarios cover repeated pause/resume, automatic resumption with changed scheduling settings, ETag/size/Last-Modified/range changes, changes during resume, corrupted bytes, replaced/truncated/hard-linked partials, corrupted ledgers, mismatching URL/checksum, unsupported streaming partial reuse, archival restart of legacy partials, fully saved checkpoints, interruption after rename, and damaged completed destinations. Transient HTTP errors, dropped segment/stream bodies, probe timeout, exhaustion with useful saved work, Retry-After, excessive server delays, permanent HTTP errors, pause during backoff, and TLS failure use the normal retry policy. Native units additionally hold actual Windows readers without delete sharing: transient contention must resolve within the bounded replacement retry; persistent contention must preserve the previous encrypted journal and remove temporary files. They also check DPAPI encryption, invalid/overlapping records, exclusive locks, exponential/jitter bounds, and reopened hashes/gap scheduling above 4 GB.

The fixtures simulate supported interruption states; they do not reboot Windows or disconnect physical storage. Contract and implementation details are in [recovery](RECOVERY.md).

## Buffered-write checks

`engine.buffered` adds 22 real transfers with independently generated/reread SHA-256. Segmented and streaming bodies cover one byte, sizes immediately below/at/above 64 KiB and 128 KiB, and sizes around 1 MiB. Checks verify correct tail flushing, byte totals, file-write/checksum-read telemetry, bounded segmented write-call counts (streaming retains direct writes), durable publications, and absence of partials after success. Two fixtures drop a response after 32,769 bytes, before a complete write buffer exists. Retries must finish with matching independent checksums, no unsigned progress underflow, and complete verified-byte totals. Existing integration/recovery groups retain malformed/truncated responses, streaming fallback, pause/cancellation, actual process death, immutable saved ranges, changed validators, trusted-checksum failures, and sparse writes/reopened hashes above 4 GB. Timings do not determine correctness acceptance.

## Browser protocol and controller checks

`browser.native` runs the actual separate host with binary frames against a real Qt application, restricted Windows named pipe, persistent queue, and controlled server. It checks wrong origins, malformed/oversized/truncated frames, unavailable app, public preflight, idempotent prepare/commit/abort, inert preparation across app restart, wrong browser size, supported streaming, unsafe destinations, changed validators, encrypted SQLite, receipt retention after history removal, and independently hashed completion. The queue group starts from an existing version-1 database to verify schema-2 migration. These tests are correctness checks, not foreign-user penetration tests.

`browser.extension` executes the actual JavaScript controller with deterministic Chrome API substitutes: cancellation order, preflight/host/cancel failures, browser completion races, worker reconstruction at preparation, lost commit acknowledgement, outage after cancellation, abort acknowledgement/restoration, user disable during preflight, and unsupported metadata. Run manually with `node tests/ExtensionTests.mjs`. Worker reconstruction there is distinct from the actual browser restart below. Native protocol tests run serially because each uses the same current-user pipe. Do not run Debug/Release native tests or actual Chrome tests together, or while the normal app owns that pipe.

## Actual Chrome test

The video update adds `browser.media` model checks and `gui.media` real Qt/yt-dlp/FFmpeg transfers. Install local helpers for both configurations with `scripts/Install-MediaTools.ps1 -Configuration Release` and `-Configuration Debug`. Without helpers `gui.media` explicitly skips (exit 77); a skip does not establish video support. The updated separate Chrome test also requires helpers, clicks the injected player button, drives the resulting native download, independently hashes its MP4 output, and checks player/button removal. Source and execution boundaries are in [media support](MEDIA.md).

`tests/ChromeTests.cjs` uses Playwright, official Chrome for Testing, Python, and the built `downshift_browser_tests.exe`/`DownshiftNativeHost.exe`. The helper displays the actual `MainWindow` and runs the same pipe, queue, and engine as the app, but stores its files in an isolated test folder. The test temporarily registers this one native host in HKCU, restores its earlier default value in `finally`, and never changes the normal Chrome profile. Run from the repository root, replacing executable paths with your own:

```powershell
node tests/ChromeTests.cjs '<Chrome for Testing executable>' build/windows-msvc/Release/downshift_browser_tests.exe build/windows-msvc/Release/DownshiftNativeHost.exe '<Python executable>' build/phase7-chrome-release
```

Playwright must be resolvable from Node or set `DOWNSHIFT_NODE_MODULES` to its module directory. Repeat sequentially with Debug paths and a separate output folder. Ordinary branded Chrome no longer supports the test's extension loading flag; use Chrome for Testing for automation, and Chrome's Load unpacked UI for user installation. See the [official Chrome announcement](https://groups.google.com/a/chromium.org/g/chromium-extensions/c/1-g8EFx2BBY/m/S0ET5wPjCAAJ).

Nine checks cover extension identity/readiness/default-disabled consent, disabled browser passthrough, actual public handoff, duplicate reconciliation, a real Chrome/process/worker restart during preparation, safe abort of the download cancelled by test-browser shutdown, new successful handoff after restart, cookie-only authentication fallback, and unavailable-native fallback. The two native completions and browser fallback files are independently reread for SHA-256. The restart check does not claim a standalone worker-only termination: closing Playwright's browser also cancels its live download, so the replacement controller correctly aborts that preparation. Worker-only reconstruction and lost acknowledgement timing are exercised separately in deterministic controller checks.

Phase 8 makes this restart boundary deterministic: the test holds the old worker's storage transition after the real native prepare acknowledgment, asserts an actual Prepared queue entry, then closes Chrome before cancellation authorization can advance. Other storage calls delegate to the real Chrome API; the temporary test-only gate dies with that worker. The replacement worker uses unmodified APIs and reconciles the persisted preparing stage. The earlier wall-clock fixture could close Chrome before native preparation existed; both safe outcomes are valid, but only the acknowledged boundary proves this intended check. Accepted Phase 8 reports are [Release](evidence/phase8-chrome-release.json) and [Debug](evidence/phase8-chrome-debug.json), nine checks each. [Local verification evidence](evidence/phase8-local-tests.json) records twelve passing CTest groups per configuration, 102.03 s Release / 105.61 s Debug, including the new buffered-transfer checks.

Accepted Phase 8 reports preserve source/executable hashes under `docs/evidence/phase8-chrome-{release,debug}.json`; Phase 7 reports remain historical. Browser profiles, files, registry backups, netlogs, and transient failures stay under ignored `build`. Local Chrome for Testing was 155.0.8059.39; archive SHA-256 `59ab2a6e99bde9c0bc180414988394f9f5355a0d3764c704151ee8ecea235c7e` (replace with the recorded download hash if comparing a different archive). The original signed executable and test-named copy both hash to `b3750f3977e4c179e80b8fcb66d5919ca6c0a6525c2f5066f7e40e1becfcd083`. The test copy avoided this machine's IDM process-name interception without changing IDM settings; see [Chrome integration](CHROME.md#testing-and-competing-browser-integrations). These controlled HTTP fixtures do not establish universal website compatibility, public Internet/TLS browser coverage, or throughput superiority.

The final Phase 8 native unit count is 12,239 in each configuration, including actual transient/persistent Windows reader locks during encrypted checkpoint replacement. An earlier Debug desktop assertion failed before detailed status/error output existed; a focused rerun and the subsequent full suites passed. That observation is retained in [verification notes](evidence/phase8-debug-desktop-observation.json); its external cause is unestablished.

The video-history fix adds actual saved-file checks before completion, persistent video records, main-list retry/cancel controls and preserved retry folders. `gui.media` exercises valid direct and merged media, verified reuse, invalid existing output skipped by a successful helper, missing output, actual helper cancellation, history across restart and interrupted-task recovery. Media rows cannot enter the native file scheduler. Chrome end-to-end checks additionally assert the completed video history and saved file hash. Close the normal Downshift app before the isolated Chrome test: its native pipe is exclusive to the Windows user. Child responses have bounded waits and fail on closed output rather than hanging silently. No tests should use or change the normal app's queue or Chrome profile.

## Independent socket regressions (0.4.1)

engine.transport runs TransportTests.py with Node's built-in TLS HTTP/2 server (TransportFixture.cjs), the disposable existing localhost certificate and an explicit per-request CA bundle. No trust-store installation or new frontend dependency is added. The fixture offers HTTP/2 and HTTP/1.1, verifies actual HTTP/2 requests, shapes bytes per physical socket, and counts simultaneous foreground sockets separately from background sockets. A one-slot and eight-slot case exercise per-socket limits; two further cases compete with four genuine HTTP/1.1 background clients under a shared fair socket budget. The model demonstrates a mechanism, not arbitrary router fairness.

Every foreground case independently verifies full size/SHA-256 and exact contiguous range coverage. Socket counts enforce pool limits and require eight physical connections for eight active slots. Unique socket counts check keep-alive reuse across sixteen ranges. Throughput guards are deliberately broad (3× for per-socket shaping and 2× for controlled contention), subordinate to the socket/correctness assertions. Existing HTTP/1.1, malformed HTTP/2 fallback, caps, pause/restart and unsafe-resume regressions remain required. Node is already used by the extension tests. New test windows remain private and hidden.

Optional live diagnosis used a read-only saved URL kept in memory and separate UUID test destinations. Bounded samples paused after 8 MiB and measured actual owning-process established TCP connections. Original user partial/journal metadata was checked unchanged. This is not full-file verification or an automated IDM throughput benchmark; do not use the final smoothed sample as a guaranteed line rate. DEVELOPMENT_PROGRESS.md records exact results and excluded preliminary helper attempts.
