# Persistent download queue

Phase 5 adds a native queue service shared by later desktop and browser clients. One service thread exclusively owns SQLite, commands, and scheduling. Each active download owns one blocking engine worker; that worker still uses libcurl multi for all of its ranges. No database or transfer work needs to run on the GUI thread. Futures carry command results and snapshots; workers expose bounded, replaceable progress mailboxes rather than an unbounded event backlog.

SQLite uses WAL, FULL synchronization, prepared statements, a versioned schema, and an exclusive process lease. IDs are random; each record's complete JSON payload is authenticated/encrypted with Windows user-scoped DPAPI before entering SQLite, including URLs, query tokens, destinations, checksums, recovery-ledger references, timestamps, status, and priority. Settings are encrypted too. SQL, WAL, and recovery sidecars contain no plaintext credentials. Database damage or a failed durable queue write stops scheduling rather than silently losing acceptance. The database is private to the current Windows account, not a protection against other software running as that account.

The range journal remains the authority for verified bytes. SQLite links to that journal and stores queue/history state; it never overrides range hashes or remote revalidation. Running jobs become paused after a crash or restart. Previously queued jobs are held unless `startOnLaunch` is enabled. Completed history stays completed. Resume uses existing encrypted journals; weak-validator partials explain why explicit Restart is needed. Restart uses the engine's archival behavior. Cancel preserves partials. Removing history preserves files. Renaming is limited to unstarted downloads, because moving an active or recoverable partial would invalidate its durable identity.

Scheduling uses stable high/normal/low priority and configurable simultaneous downloads (1-16), downloads per original URL origin (1-16), and a conservative per-origin connection reservation. Priority changes affect future assignments without interrupting active work. Each job reserves at most `floor(hostConnections / perHost)` connections, minimum one; downloads per host are capped by available connection slots. Redirect destinations are not globally pooled across independent engines: these limits govern the submitted origin. Global and per-download byte pacing include retried body writes, use bounded callback buffers, and poll cancellation while waiting. A cap is a pacing limit rather than an Internet link-speed guarantee. Slow pacing can reduce adaptive slot growth and throughput; unlimited remains the default. Engine network validation and final checksums are unchanged.

Tests drive the actual native queue through a small development-only JSON console helper. They download independently hashed loopback files, verify concurrency and bandwidth bounds, priorities, pause/resume, cancellation, encrypted persistence, exclusive ownership, malformed-input rejection, history/settings restart, real process death, recovery, and visible corruption failure. This helper is not an end-user interface or browser protocol.

Phase 6 provides desktop controls. Phase 7 adds staged browser acceptance. Installer/portable distribution remains Phase 9.
