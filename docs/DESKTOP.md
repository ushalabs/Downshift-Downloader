# Downshift desktop

Run `build/windows-msvc/Release/Downshift.exe` from the project after building. This is the development executable with its adjacent runtime DLLs and platform plugins; an installer is a later phase.

Add download accepts an HTTP/HTTPS link, an explicit destination, optional trusted SHA-256, priority, per-download speed limit, and whether to start immediately. The engine validates the link and destination on a worker before durable acceptance. Existing files and partials are preserved. Select a row to use Resume, Pause, Cancel, and More. Restart archives a partial and fetches again after confirmation. Unstarted jobs can change filename. History removal leaves files intact. Completed-file deletion requires confirmation and runs through an exclusive, non-reparse, single-link Windows file handle on the queue service. Opening any downloaded file requires an explicit user action and confirmation; Downshift never executes a download automatically.

Search matches filenames/destinations and source links. Filters select all, in progress (including paused), completed history, or failures/cancellations. Live rows display size, downloaded bytes, progress, speed, time remaining, connections, status, and priority. The details panel includes source/destination, rates, elapsed/remaining time, verified-byte progress, connection counts, resume capability, and errors. Unknown lengths show a dash instead of a fabricated percentage. An aggregate speed shows only currently running workers. Verified bytes can be lower than received bytes until a range finishes and its digest/checkpoint is durable.

Settings persist the download folder, simultaneous/per-site download and connection limits, auto/fixed connections, aggregate speed limit, light/dark appearance, queue startup behavior, completion notifications, and basic diagnostics. Connection changes apply to new workers. Aggregate cap changes wake old pacing waits and take effect on later body callbacks. Notifications use Windows' tray support where available, with a status-bar completion message. Basic activity logs rotate at about 1 MB and contain only timestamps, random IDs, and status names; they never include URLs or server messages. Chrome status is provided by the Phase 7 integration.

The database is `%LOCALAPPDATA%\Usha Labs\Downshift\queue.sqlite`. Network, file writes/hashes, database operations, deletion, and scheduling run outside the GUI thread. The GUI polls a single asynchronous snapshot at 250 ms intervals and updates existing rows/widgets. Command results use short asynchronous timers and lifetime guards. OS file dialogs and explicit Windows open actions run as normal user interactions. Closing the window ends the application and cooperatively pauses active workers before releasing the database. It does not silently continue downloads in a hidden tray process. Startup holds interrupted work for explicit Resume.

`gui.integration` manipulates real Qt buttons and dialogs against a bounded loopback server, pauses/resumes a checksum-verified file, checks search/filters, settings Save/Cancel, light/dark rendering, validation feedback, persistent history, explicit worker deletion, and event-loop heartbeat. Python independently rereads a copy of the completed file. BMP test captures use Qt's built-in codec; repository PNG screenshots are conversions of those actual captures, not mockups. Screenshots depict test files and local fixture paths. Heartbeat gaps are test observations, not general startup/throughput guarantees.

The Chrome settings status **Ready for the extension** means the local pipe is active; it does not prove host registration or extension installation. The extension popup performs the complete connection check. Browser-prepared rows show **Awaiting Chrome** and cannot start through Resume/Restart. Their More action can durably abort the pending handoff. Follow [Chrome setup and recovery](CHROME.md).
